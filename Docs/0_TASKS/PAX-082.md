## 1. Why

- The developer judges the movement wrong on all three counts.
- Every window, lead and reach check the harness measures depends on these numbers.
- If the feel changes after KIT-4, every KIT-4 threshold, route result and shipped window has to be measured again.
- So the feel gets fixed once, now, and everything is re-measured once.

## 2. What to build

Two stages. The developer's tuning session sits between them.

### 2a. Tuning support (only as much as Phase 1 shows is needed)

- **Live editing.** The developer edits the `CatMotorConfig` asset in the Inspector during Play and feels the change at once.
  - If the motor already reads the config every step, nothing is built for this.
  - If it caches values, Phase 1 names where. The smallest fix is to re-read the values on `OnValidate` in the Editor only. That needs a ruling (§5).
- **A dev readout** (DebugTools, excluded from release builds). On screen during Play, derived from the live config:
  - apex height;
  - airtime;
  - the maximum horizontal jump reach, and the 0.75 fraction of it that the validator allows (D-056 (2));
  - run speed in units per second and per tick.
  - **It uses the validator's own reach math**, not a copy, so the readout and the validator can't disagree.
- **Falling-block speed and delay while tuning.** In Play, the developer changes a block's `unitsPerTick` and `delayTicks` on the scene object. These are throwaway edits for feel; the chosen values reach the layouts in 2b.
- **Stop after 2a.** Report what was built, then wait for §0.

### 2b. Commit the numbers and measure again (after §0)

1. **The config asset:**
   - write §0's run and jump values into `CatMotorConfig.asset`;
   - add a pin test that asserts them.
2. **Falling blocks:**
   - apply §0's speed (and delay, if changed) to every FallingBlock in `L001Layout`–`L004Layout` and `TrapLabLayout`;
   - if Phase 1 finds a kit-wide default, change it there too.
   - Geometry doesn't change here.
3. **Measure again** with the harness:
   - every route (`ValidateRoutes`): L001–L004 and Trap Lab rooms 0–4;
   - every layout validator rule: reach, slack, door clearance, surface coverage, arrows;
   - windows, leads, and the betrayal outcomes (dies / recovers).
4. **Re-pin:**
   - `ShippedRouteResultsTests`, TrapLab3 and TrapLab4 get the new measured values, reported as a table (old → new);
   - D-080's rule for pinned results still applies: a pin changes only to the new measured value.
5. **The box-model tests:** remove D-079 (7)'s redundant tests now:
   - `ShippedLevelTimingTests`' Lift test and its two L004 tests, including `L004_EarlyFlipBand_IsKilledByBlock1`;
   - `RoomStepper`, if nothing else uses it.
   - They model the old motor, and the harness replaces them (D-079 (4), D-081 (5)).

## 5. Rules

- **Runtime code:**
  - If 2a needs live editing and the motor caches values, the fix is an Editor-only re-read; it needs a ruling first.
  - The readout lives in DebugTools.
  - No other change to runtime Gameplay or Core code.
  - The movement *model* doesn't change. No variable jump height, no acceleration curves, and no new trap motion (§8).
- **Unchanged:**
  - the thresholds (12, 6, 30, and 0.75 reach);
  - the tick rate (50 Hz);
  - coyote and buffer in seconds (D-077). Their tick counts come from `TickTime`; report them if they change.
- The door clearance follows from the new MaxSpeed automatically (D-075 (5)). Report the new margin.
- Tests are deterministic only. Tests that open scenes restore the Test Runner's scene (CLAUDE.md).

## 12. Rulings on the 2a questions (R1–R7)

**ACCEPTED:** the pre-flight (618 in 60.6 s), the Phase 1 trace, and 2a as built (`JumpReach`
moved to Core with identical arithmetic, `MovementReadout`, and 2 tests, both seen red; total 620).
Moving the panel after the test run is fine; the first 2b run covers it.

**R1 · The readout: a menu toggle, with no scene change.**
- `PARALLAX/Debug/Movement Readout` is a checkable Editor menu storing an EditorPrefs bool, off by
  default.
- `MovementReadout` gets a `[RuntimeInitializeOnLoadMethod(AfterSceneLoad)]` inside
  `#if UNITY_EDITOR`. When the bool is on, it creates one hidden-in-hierarchy GameObject with the
  readout, marked `DontDestroyOnLoad`. When it's off, it does nothing.
- No setup menu, and no scene is saved.
- Allowed: one new Editor file for the menu, and its `.meta`.
- Test: with the pref off, the hook creates nothing. Test that part only; mark the rest "unproven
  (Editor Play)".
- Accepted as built, including the `Application.isPlaying` guard on `DontDestroyOnLoad`.

**R2 · The block delay: no code.** `delayTicks` is read in `Awake`, so the developer changes it on
the block's scene object BEFORE pressing Play, plays, and repeats. The scene is never saved (§9).
Fall speed stays live during Play.

**R3 · The jump's shape: gravity is allowed.**
- The developer may tune `GravityReceiver.strength` during Play, in addition to `jumpHeight` and
  the run values. `jumpHeight` sets the apex; gravity sets airtime, how floaty the jump feels, and
  how fast the cat falls.
- 2b allowed files: `Cat_Player.prefab`, the `GravityReceiver.strength` field only.
  - First list every scene or prefab that overrides strength (Level_00N, Trap Lab, the sandboxes).
  - A level-scene override is refreshed by the developer's Rebuild All Levels.
  - Sandbox overrides are outcome (d): report them, don't fix them.
- The same `GravityReceiver` also serves the frozen co-op code. A changed strength there is outcome
  (d), report only. No code change.
- `maxFallSpeed` (20) is tunable too, as a config field.
- Finding (noted): only `Cat_Player.prefab` sets strength (30); no scene overrides it. Every cat,
  including the co-op sandbox's, is a plain instance, so a new gravity reaches the co-op sandbox
  too: outcome (d), report only.

**R4 · TickTimeTests:** add `TickTimeTests.cs` to the 2b files.
