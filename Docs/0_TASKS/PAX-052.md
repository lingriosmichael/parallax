## 0. What rev B replaces

Rev A framed one room on one screen. Since then, D-069 allows rooms wider than one screen, and
the PAX-051 review found two gaps:

- `Rebuild All Levels` rebuilds only the room, so scaffolding changes never reach existing level
  scenes.
- `BakedBounds_…` recomputes bounds from the layouts instead of reading them from the scenes.

This ticket fixes all three things at once: the camera is the first scaffolding change, so the
regeneration path has to exist before it lands.

## 1. Why

50 level scenes can't be hand-fixed each time the HUD, camera, pause menu, audio or art changes.
`_LevelTemplate` becomes the single source of every level's non-room content, and a level scene
becomes a pure function of template plus layout (D-054, extended). The camera then has to show a
whole troll room at once, and follow the cat through precision rooms without hiding the next
landing.

## 2. What to build

### 2.1 Template-driven level scenes (D-070)

1. **`Rebuild All Levels` and `Rebuild Current Level` regenerate the whole scene**, not only the
   room: template copy → `SoloRoomBuilder` → bake bounds → configure the level camera (§2.2) →
   save. `New Level…` uses the same function. There must be one code path for all three.
2. **Scene identity is stable.** Regenerating `Level_NNN.unity` keeps its `.meta` GUID, so Build
   Settings and any GUID reference keep working. Overwrite the scene in place; never
   delete-and-copy. Phase 1 names the exact mechanism.
3. **Deterministic.** Running `Rebuild All Levels` twice in a row must leave `git diff` empty after
   the second run.
4. **`Build Level Template` becomes bootstrap-only.** It creates `_LevelTemplate` from
   `Level_Solo01` only when the template is missing. The "rebuild" option is removed, because
   from now on the template holds scaffolding changes that `Level_Solo01` doesn't have.
5. **Scaffolding menus target the template.** Any setup menu that configures level scaffolding
   (the new camera menu here, and later ones) has a scene guard that accepts only
   `_LevelTemplate`. After running one, the developer runs `Rebuild All Levels`.
6. The guards from PAX-051 still apply. Level menus refuse to run in `Sandbox_Realities`,
   `Level_Solo01` and unlisted scenes. The regeneration menus also refuse to run in
   `_LevelTemplate` itself.

### 2.2 Level camera (D-071)

A level camera on `Camera_A`. It is world-aligned (D-020), orthographic, and reads only the
bounds baked into `RoomManager` (D-059), never a layout (D-066). Pure math goes in
`Parallax.Core` (reuse or extend `CameraMath` if Phase 1 shows it fits); the component goes in
`Parallax.Gameplay`.

1. **Fit mode.** If the room's bounds plus a margin fit in a view no taller than
   `MaxViewHeight` at the current screen aspect, the camera is static. It is centred on the room
   and sized to show the whole room plus the margin. This is the default for troll rooms: the
   player sees the whole room.
2. **Follow mode.** Otherwise the view height is `min(room height + margin, MaxViewHeight)`, and
   the camera follows the cat:
   - dead zone and smoothing, reusing PAX-012's clamp-before-`SmoothDamp` rule;
   - a horizontal look-ahead of `LookAhead` units in the cat's direction of travel, so the next
     landing is on screen;
   - clamping, so the view never shows beyond the room bounds plus the margin;
   - vertical follow only when the room is taller than the view.
3. **Snap on reset.** When the room resets after a death (D-041), the camera jumps straight to
   its clamped position for the checkpoint, with no smoothing. The ≤ 0.75 s reset must not turn
   into a camera swoosh. During the death hold (D-058) the camera doesn't move.
4. **Aspect.** The mode and size are recomputed when the screen aspect changes. Tests cover
   16:9, 20:9 (Pixel 8a) and 4:3.
5. **Constants.** `MaxViewHeight`, `Margin`, `LookAhead`, the dead zone and the smoothing time
   are named constants in one place. Phase 1 proposes starting values from `Camera_A`'s current
   settings in `Level_Solo01` and the sizes of rooms 1–4. They get tuned on the device later.
6. **Setup menu.** `PARALLAX/Setup/Levels/Level Camera` configures `Camera_A` in `_LevelTemplate`
   only. The regeneration step (§2.1) wires each level's camera to that scene's `RoomManager`.
   `Camera_B` and `RealityRoot_B` stay untouched (frozen co-op). `CatCameraFollow`'s behaviour in
   `Sandbox_Realities` must not change.

### 2.3 Background per level

Phase 1 reports what `RealityRoot_A/Background` (and `Foreground`) are. At build time, the
regeneration step positions and sizes the background from the baked bounds, so it covers
everything the camera can show in either mode. No new art, and no parallax scrolling.

### 2.4 Scene-read bounds test

A test opens each listed `Level_NNN.unity` and `Level_Solo01.unity` read-only. It asserts that
each level's baked `RoomManager` bounds equal `Level_Solo01`'s room N bounds, translated to local
space. The test never saves or dirties a scene and restores the scene setup it started with. The
existing `BakedBounds_…` test stays as it is.

## 4. Rules

- `Level_Solo01.unity`, `Sandbox_Realities.unity`, `SoloRoomsLayout.cs` room data and every
  existing test stay untouched.
- Frozen co-op code stays untouched. `Camera_B` stays disabled and unmodified.
- Nothing reads a layout at runtime (D-066).
- Level scenes change only through the regeneration menus.
- No new traps, no new element kinds, and no layout changes.

## 5. Tests (EditMode)

1. **Fit mode:** a small room at 20:9 gives a static camera centred on the room; the whole room
   plus the margin is visible, and the size is the minimum that shows it.
2. **Follow mode:** a room wider than the fit limit gives follow mode, with view height
   `min(room + margin, MaxViewHeight)`.
3. **Clamp:** with the cat at the far left or right edge, the view never extends past the bounds
   plus the margin.
4. **Look-ahead:** moving right shifts the target right by `LookAhead`, and moving left shifts it
   left; both stay clamped.
5. **Aspect:** the same room at 16:9, 20:9 and 4:3 gives the expected mode and size for each.
6. **Snap:** after a reset, the camera position equals the clamped checkpoint target in the same
   step, with no smoothing residue. During the death hold the camera doesn't move.
7. **Scene-read bounds** (§2.4).
8. **Level scenes:** each listed scene has the level camera on `Camera_A`, wired to its own
   `RoomManager`; each Build Settings GUID resolves to its `Level_NNN.unity` path.
9. **Guards:** the regeneration and camera menus refuse the scenes named in §2.1.6. Test the
   guard function, not the menu.

Every test must fail before the code exists, for the reason named. No existing test is modified.

## 7. Decisions to write as built

- **D-070 · Level scenes are generated.** `_LevelTemplate` is the only source of a level's
  non-room content. A level scene is regenerated as template + layout by one code path (New,
  Rebuild Current, Rebuild All). Scene GUIDs stay stable, regeneration is deterministic, and hand
  edits to level scenes are not supported. Scaffolding menus target the template only.
  `Build Level Template` is bootstrap-only.
- **D-071 · Level camera.** Fit mode versus follow mode and the rule that picks between them,
  the named constants and their starting values, look-ahead, the clamp, snap on reset, and a
  still camera during the death hold. It reads only baked bounds. Record that trap-reveal
  visibility in follow rooms is checked by the validator in the kit tickets (KIT-2, KIT-4), not
  by the camera.

## 8. Out of scope

- Level select (PAX-053) and pause (PAX-054).
- Retargeting existing scaffolding menus (listed in Phase 1 only).
- Camera shake and zoom effects.
- Parallax backgrounds and new art.
- Trap-visibility validation (KIT-2, KIT-4).
- Tuning constants on the device.
- Any change to `Level_Solo01`.
