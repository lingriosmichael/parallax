# PAX-051 · One-room level authoring pipeline

**Status:** Approved for implementation once PAX-050 is committed
**Phase:** Solo v1, Phase B (one-room levels and flow)
**Depends on:** PAX-050 committed (EditMode baseline = PAX-050's total)
**Decisions:** D-062 (level = one room), D-063, D-064, D-054 (layouts are data), D-053, D-056,
D-057, D-058/D-059 (kill bounds), D-060 (door clearance)
**Implementer reads first:** `Docs/07_DECISIONS.md` (D-054, D-059, D-060, D-063, D-064),
`CLAUDE.md`, then `SoloRoomsLayout`, `SoloRoomsSetup`, `TrapLabLayout`/`TrapLabSetup`, the existing
layout validators and their tests, `RoomManager` (`RoomBoundsEntry[]`), `LevelListConfig`,
`LevelCompleteUISetup` (scene guard pattern).

---

## 1. Why

v1 needs 50 levels, each one room (D-062). Today rooms are built by `SoloRoomsSetup` from one
multi-room `SoloRoomsLayout` into `Level_Solo01`. Making 50 levels that way is slow and error
prone. This ticket makes "a new level" a data asset plus one menu click, and makes every listed
level pass the layout rules in tests, so Phase D is design work, not plumbing.

## 2. What to build

1. **`LevelLayout`** (`Parallax.Gameplay`, `ScriptableObject`, one asset per level under
   `Assets/_Game/Data/Levels/`): exactly one room, described with the **same element types**
   `SoloRoomsLayout` uses (geometry, checkpoint, door, every trap and its settings). If those
   element types can't be serialized inside a ScriptableObject without changing them, stop and
   report (Phase 1, Q2).
2. **`LevelListConfig` entries gain `Layout`** (reference to the level's `LevelLayout`). The
   existing `Id`/`SceneName`/`DisplayName` stay. Convention: id `L001`…`L050`, scene
   `Level_001`…`Level_050` under `Assets/_Game/Scenes/Levels/`.
3. **Level template scene** `Assets/_Game/Scenes/Levels/_LevelTemplate.unity` (created by the
   menu, not by hand): everything a level needs except the room — cat, `RoomManager`,
   `RoomDeath` + `RoomSafetyConfig`, input router, touch controls, HUD, level-complete screen
   (PAX-049/050 wiring), camera. Built by reusing the existing setup menus in order, not by
   duplicating their code.
4. **Menus** (extend `PARALLAX/Setup/…`, idempotent):
   - `PARALLAX/Setup/Levels/New Level…`: asks for the next free number, creates the
     `LevelLayout` asset (one checkpoint, one door, a floor), the scene from the template, builds
     the room from the layout, appends the entry to `LevelListConfig`, adds the scene to Build
     Settings (this ticket explicitly permits that), saves the scene.
   - `PARALLAX/Setup/Levels/Rebuild Current Level`: in an open `Level_NNN` scene, deletes the
     room root and rebuilds it from its `LevelLayout` (D-054: the scene always equals the data),
     recomputes kill bounds, saves.
   - `PARALLAX/Setup/Levels/Rebuild All Levels`: the same for every listed level, opening and
     saving each scene, then restoring the originally open scene. Reports per-level success.
   - Refuses in `Sandbox_Realities` and any scene not in `LevelListConfig`.
5. **Seed levels**: split `Level_Solo01`'s four rooms into `L001`–`L004` (`Level_001`–
   `Level_004`), one room each, same geometry and traps, translated so each room's checkpoint
   sits at the level origin. `LevelListConfig` lists exactly `L001`–`L004`; `Level_Solo01` is
   dropped from the list but stays in the repo, untouched, as a reference. The first scene in
   Build Settings stays whatever PAX-050 left until PAX-053 adds the menu scene.
6. **All-levels validation**: one EditMode fixture iterates every `LevelListConfig` entry and
   runs the existing layout validators on its `LevelLayout` (D-056 slack/reach, D-057 lead,
   D-058 bounds, D-060 door clearance, D-055 chain rules). Nothing is re-implemented; if a rule
   only exists inside a test for `SoloRoomsLayout`, move it into a reusable validator in
   `Parallax.Gameplay`/`Core` without changing its logic, and keep the old test calling it.

## 4. Rules

- The level is data (D-054). No level-specific code, no per-scene hand tuning saved to disk.
- `SoloRoomsLayout`, `SoloRoomsSetup` and `Level_Solo01.unity` stay untouched (reference and
  regression). Frozen co-op code stays untouched.
- Build Settings may be changed **only** by the `New Level…` menu, appending a level scene.
- A level has exactly one checkpoint and one door; validation rejects 0 or 2+.
- Menus are idempotent: running any of them twice leaves the same result.

## 5. Tests (EditMode, required)

1. Every `LevelListConfig` entry has a `Layout`, a unique `Id`, and a `SceneName` that exists in
   Build Settings (read via `EditorBuildSettings`).
2. Every listed layout has exactly one room with one checkpoint and one door.
3. Every listed layout passes D-056, D-057, D-058 (checkpoint and door inside bounds), D-060.
4. `L001`–`L004` contain the same elements as `SoloRoomsLayout`'s rooms 1–4, up to the per-room
   translation (a structural equality check, so the split lost nothing).
5. A layout with two doors, or a door outside bounds, fails validation with a message naming the
   level id.
6. Kill bounds computed for `L00N` equal `Level_Solo01`'s room N bounds, translated.

Tests fail for the right reason before the code exists. No existing test is modified, except
where a rule moves into a reusable validator (then the old test calls it; say so in the output).

## 6. Allowed files

- New files under `Assets/_Game/Gameplay`, `Assets/_Game/Core`, `Assets/_Game/Data/Levels`,
  `Assets/_Game/Editor/Setup`, `Assets/_Game/Tests/EditMode`
- `LevelListConfig.cs` (add `Layout`), the `LevelListConfig` asset (via menu only)
- Validator source files, only to extract an existing check into a reusable class
- Scenes under `Assets/_Game/Scenes/Levels/`: created by the menu only

## 7. Out of scope

Camera framing (PAX-052) · menus (PAX-053/054) · new traps · designing new rooms · difficulty
tiers (PAX-057) · deleting `Level_Solo01`.
