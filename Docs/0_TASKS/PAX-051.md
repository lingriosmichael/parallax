## 0. What changed from rev A, and why

The trace showed three things rev A got wrong:

- **Layouts are only ever needed at edit time.** The scene is built from the layout by a setup
  menu, and kill bounds are baked into `RoomManager` at setup (D-059). Nothing reads a layout at
  runtime. So a level layout doesn't need to be a ScriptableObject or live in
  `Parallax.Gameplay`. It stays what `SoloRoomsLayout` already is: **code-as-data in the Editor
  assembly, built from the existing readonly types.** None of options A/B/C is used: no type
  changes, no forked types, no JSON.
- **No menu chain builds a level's non-room scaffolding.** The template scene is made by
  copying `Level_Solo01` and stripping its rooms, via a menu, not rebuilt from scratch.
- **The D-056–D-060 checks live only in test code**, mixed with room-specific assertions. Only
  the generic rules are extracted; the existing tests stay untouched.

## 1. Why

Unchanged: v1 needs 50 one-room levels, so "a new level" must be one layout file plus one menu
click, and every listed level must pass the layout rules in tests.

## 2. What to build

1. **Level layouts as code.** One file per level, `Assets/_Game/Editor/Levels/L001Layout.cs`
   etc., each a static class exposing one `SoloRoomDefinition` built with the existing
   constructors. Levels live in their own local space: checkpoint at the origin, room id 0.
2. **`LevelLayouts` registry** (Editor): the single map from level id to layout. Every
   `LevelListConfig` entry must have a registered layout, and every registered layout must be
   listed (tested both ways).
3. **Type declarations out of `SoloRoomsLayout.cs`**, only if they are declared in that file:
   move `SoloRoomElement`, `SoloRoomTrapSettings`, `SoloRoomOpening`, `RequiredJump`,
   `RequiredStep` and `SoloRoomDefinition` **verbatim** into their own file(s) in the same
   assembly and namespace. The room data in `SoloRoomsLayout.cs` is not changed. This is the
   only edit allowed to that file, and it lets later kit tickets extend the types without
   touching the reference data.
4. **`SoloRoomBuilder`** (Editor): extract the room-building part of `SoloRoomsSetup.Configure()`
   into a function that takes a scene context plus `SoloRoomDefinition[]`. `SoloRoomsSetup`
   calls it with `SoloRoomsLayout`'s rooms. **Regression proof:** after the refactor, rerunning
   `SoloRoomsSetup` on `Level_Solo01` must leave `Level_Solo01.unity` byte-identical in git
   (`git diff --stat` empty after save).
5. **Template scene.** `PARALLAX/Setup/Levels/Build Level Template` copies `Level_Solo01.unity`
   to `Assets/_Game/Scenes/Levels/_LevelTemplate.unity` (`AssetDatabase.CopyAsset`; the
   original is never opened for writing). It opens the copy, deletes every room root, clears
   `RoomManager`'s bounds, and saves. The output lists every root object left in the template;
   the developer reviews that list. Idempotent: it refuses if the template exists unless asked
   to rebuild.
6. **Menus** (idempotent, extend `PARALLAX/Setup/Levels/…`):
   - `New Level…`: takes a registered level id with no scene yet. It copies the template to
     `Level_NNN.unity`, builds the room with `SoloRoomBuilder`, bakes bounds, appends the entry
     to `LevelListConfig`, adds the scene to Build Settings (this ticket permits that), and
     saves.
   - `Rebuild Current Level`: deletes and rebuilds the room from its layout (D-054), rebakes
     bounds, and saves.
   - `Rebuild All Levels`: runs the same for every listed level, reports per level, and restores
     the scene that was open.
   - All three refuse in `Sandbox_Realities`, `Level_Solo01` and any unlisted scene.
7. **Seeds.** `L001`–`L004` are `Level_Solo01`'s rooms 1–4, converted to local space (checkpoint
   at the origin, room id 0). `LevelListConfig` becomes exactly `L001`–`L004`. The
   `Level_Solo01` entry is removed from the list; the scene stays in the repo and in Build
   Settings. The old `Level_Solo01` PlayerPrefs keys are simply orphaned (dev data only).
8. **Generic validator** (Editor, next to or inside `TrapLayoutValidator`):
   `LevelLayoutValidator.Validate(id, SoloRoomDefinition) → list of errors`. It covers only the
   generic rules, reimplemented from the tests' logic without changing any threshold:
   - D-056 reach and timing slack;
   - D-057 6-tick reveal lead;
   - D-058 every element and moving pose inside bounds, with checkpoint and door inside;
   - D-060 door clearance;
   - D-055 acyclic, same-room chains;
   - exactly one checkpoint and one door.
   Thresholds come from named constants in one place (PAX-057 turns them into tier configs).
   Room-specific narrative tests stay where they are, unmodified.

## 4. Rules

- `SoloRoomsLayout.cs` room data, `Level_Solo01.unity` and every existing test stay untouched.
  The only allowed change to `SoloRoomsLayout.cs` is the verbatim type move in §2.3, and only if
  it is needed.
- No change to the element types themselves: no new fields, no readonly removal.
- Build Settings change only through `New Level…` (append).
- No level-specific runtime code. Frozen co-op code untouched.

## 5. Tests (EditMode)

1. Registry ↔ `LevelListConfig`: every entry is registered and every registered id is listed;
   ids are unique; each `SceneName` is in Build Settings.
2. Each listed layout has exactly one checkpoint and one door.
3. `LevelLayoutValidator` passes on every listed layout.
4. **Parity:** the validator also passes on each of `SoloRoomsLayout`'s four rooms, proving it
   agrees with the existing tests on known-good data.
5. **Negative cases** fail with the level id in the message: two doors; door outside bounds;
   jump beyond 0.75 reach; slack below 12 ticks; reveal lead below 6; a chain cycle.
6. **Split fidelity:** `L00N` equals `SoloRoomsLayout` room N, element by element, up to
   translation and room id.
7. Baked bounds for `L00N` equal `Level_Solo01`'s room N bounds, translated.

Tests fail for the right reason before the code exists. No existing test is modified.

## 7. D-065 (write as built)

Level format: code-as-data layouts in the Editor assembly, one class per level, local space,
registry as the map to `LevelListConfig`; scenes are copies of `_LevelTemplate` with the room
built by `SoloRoomBuilder`; nothing reads layouts at runtime, and anything runtime needs is
baked at setup (as D-059 does for bounds). Record why a ScriptableObject format was rejected.

## 8. Out of scope

Camera framing (PAX-052) · menus (PAX-053/054) · new traps · new rooms · tiers (PAX-057) ·
deleting `Level_Solo01` · cleaning up `SoloRoomsLayoutTests.cs`.
