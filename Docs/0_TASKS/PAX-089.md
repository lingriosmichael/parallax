# PAX-089 · Kit cleanup after KIT-5–KIT-9 (before levels 11–20)

**Status:** Approved for implementation. **Wait after Phase 1:** post the trace and stop.
**Phase 1 size: Lite.** No new mechanic. Phase 1 locates each item, confirms the files, and flags any item that would change runtime behaviour.
**Phase:** Solo v1, last ticket before PAX-060 (levels 11–20).
**Depends on:** PAX-088 committed. EditMode baseline = the developer's Run All after PAX-088 (expected 1034).
**Decisions it touches:** D-078, D-080 (chains), D-086–D-090 (the five new kinds). A new **D-091** only if item B changes what a chain can do at runtime (Phase 1 says).

**Menus are the developer's job.** Don't run setup menus or modify scenes through MCP.

---

## 1. Why

KIT-5–KIT-9 each left the same few gaps: their validator rules only run when a test calls them by name, two new kinds can't start a chain, and small nits piled up. PAX-060 will build ten hard levels out of these parts, so each gap would turn into a bug that's hard to trace. Every item is independent: if one gets stuck, report it and move on.

## 2. What to do

**A. Every level runs every kit rule (the main item).**
1. One aggregator, `LevelLayoutValidator.ValidateKit(layout, motor, thresholds)`, that runs, in a fixed order: `ValidateSpear`, `ValidateInverter`, `ValidateGeyser` + `ValidateGeyserEnvelope`, `ValidateVine`, `ValidateStormCloud`, and `ValidateBand`. It returns every error, not just the first. `Validate()` itself does **not** change (the existing convention).
2. One test class, `LevelKitRulesTests`, that runs `ValidateKit` over **every** `LevelLayouts` entry and over Trap Lab rooms 6–10. It passes today (no level uses the new kinds yet). Seen red by adding a broken spear to a fixture level.
3. Route-level rules that need a replay (`ValidateVineRoutes` and the like) join the existing per-level route test, not the static aggregator. Phase 1 lists which ones exist.

**B. Inverters and snap vines can start a chain.**
- `TrapLayoutValidator` accepts an `Inverter` and a snap `ClimbVine` as chain **sources** (they fire at a known tick like any trap). A plain vine without snap settings never fires, so it's still rejected as a source, with a clear message.
- Phase 1 checks that the runtime chain already works for both. If it does, this is validator-only. If either needs a runtime change, stop and report (that's D-091).
- Tests: an inverter chaining a falling block, and a snap vine chaining hidden spikes; each fires on the right tick (seen red before the validator change).

**C. "No climbing while seated" gets a test.**
PAX-087 zeroes `Climb` in `LocalHumanDriver` while the cat is seated, but it's untested because seating needs the frozen Control Station. Find a way to test it **without editing frozen code** (for example, a test-only `CatSeat` state the driver already reads). If there's no way, say so, and D-089's limitation stays as written.

**D. Split `TrapKitSetup.cs`** (401 lines, at the ~400 guideline) into per-kind builder files (for example, `TrapKitSetup.Arrows.cs`, `.Climb.cs`, `.Weather.cs` as partials). **No behaviour change:** after the split, running the Trap Lab menu and `Rebuild All Levels` must give the same objects, components and values (D-070's data-level determinism). `SavedSceneSyncTests` stays green without re-saving anything.

**E. Storm cloud nits (PAX-088 review).**
1. The cloud object keeps a trigger box at its authored pose that does nothing. Remove it, or if the wake trigger needs it, rename it so its role is obvious.
2. The trap picks the cat's first non-trigger collider, while the harness uses `GetComponent`. Make both use one shared helper so they can't drift if the prefab ever gets a second collider.

**F. Docs.**
- `02_ARCHITECTURE.md`: that file belongs to the Architect. List anything it's missing about KIT-5–KIT-9 in your output instead of editing it.
- Roadmap status line, and D-091 only if B needed it.

## 4. Rules and stop conditions

- No gameplay behaviour changes, except B's chain acceptance if Phase 1 shows the runtime already supports it.
- Every pinned route result and every existing test stays identical. A moved pin is a stop condition.
- Frozen code stays untouched (C).
- New tests red-first; report which by name.
