## 1. Goal

Two runtime changes that make deaths fair and soft-locks impossible:

- **Death hold.** Today `RoomDeath.Kill` resets the room synchronously, so the player never sees
  what killed them (D-057 had to settle for "visible before the kill"). After this ticket a death
  **freezes the room for a short hold**, showing the fired state (the gap, the revealed spikes,
  the block that landed), then resets exactly as today.
- **Out-of-bounds kill.** A cat that leaves its room's bounds dies like any other death. PAX-046
  found an endless fall through an undeclared gap; the layout was fixed, but a future layout
  mistake must never soft-lock the player again (D-053).

## 2. What stays true

- D-041: death resets the room. The reset itself (cat to checkpoint, every trap restored,
  `RoomLifeTick` back to 0) is unchanged; only **when** it happens moves.
- D-044: no lives, unlimited retries. A death counts once.
- D-054: bounds come from layout data, computed by setup code. Never hand-placed.
- D-055 timing: traps run on integer ticks; after a reset, the first live tick is `RoomLifeTick`
  0.
- Co-op code stays frozen (D-047). Don't touch co-op paths; if a shared path must change, keep
  co-op behaviour identical and say so.

## 3. Decision D-058 (commit before implementation)

```
### D-058 · 2026-09-22 · Accepted
**Decision:** Death hold and out-of-bounds kill (PAX-047).
(1) Death hold. A death freezes the room for HoldTicks (default 30 = 0.5 s at 60 Hz, in a config
asset) before the existing reset runs. During the hold: no trap steps and RoomLifeTick does not
advance (the room shows the exact state at the kill); the cat is frozen where it died and takes
no input; input given during the hold is discarded, so nothing pressed during the hold (e.g. a
buffered jump) acts after the reset; further kills, door touches and trigger entries are
ignored. The death counts once, at the kill. HoldTicks 0 reproduces today's synchronous reset.
(2) Out-of-bounds kill. Each room has kill bounds computed from its layout (every element's
bounds plus a margin, default 2 u). The room's checkpoint and door always lie inside its bounds.
A cat whose centre leaves the bounds of its current room is killed through the normal death
path (hold, then reset) and a warning names the room and position, because it means the layout
has a hole.
(3) Learnability. With the hold, D-056 (5) applies again as written: every betrayal's result is
visible after the death until the reset. D-057's 6-tick visible lead before a kill stays in
force.
**Why:** Deaths must teach (D-040, D-053): the player needs to see what killed them. And no
layout mistake may soft-lock a room.
```

## 4. Death hold semantics

Specify these before code (PAX-045 lesson: every open semantic became a bug):

| Case | Rule |
|---|---|
| Kill during live play | Death count +1, hold starts at that tick. |
| Kill during a hold | Ignored. No count, no restart of the hold. |
| Trap phase during a hold | Skipped entirely: no `StepTiming`, no chain fires, no moving-trap poses, no falling-block motion, no rearms. |
| `RoomLifeTick` during a hold | Frozen at the kill tick. |
| Cat during a hold | Frozen at its death position: velocity zero, no gravity, motor not stepped, visible (no death animation; that is PAX-A07). **Freeze method:** prefer `RigidbodyConstraints2D.FreezeAll` (or kinematic) with velocity zeroed, restoring the previous constraints/body type at reset. **Do not** use `Rigidbody2D.simulated = false` unless Phase 1 shows it fires no `OnTriggerExit2D`/`OnCollisionExit2D` (Physics2D "Callbacks On Disable" fires exits by default). |
| Input during a hold | Discarded. The command source is not read for movement, and any latched/buffered input (jump latch, jump buffer) is cleared at the reset so tick 0 starts with no pending press. A key still physically held at tick 0 counts as held, as today; only presses made during the hold are dropped. |
| Door touch during a hold | Ignored. |
| Trigger entries during a hold | Ignored (a frozen cat inside a trigger does not fire it after the reset either: the reset clears presence as it does today). Gate this in one place (e.g. a single `IsHolding` check in the shared trigger/door dispatch), not per component. |
| End of hold | Run the existing reset path unchanged. The next tick is `RoomLifeTick` 0. |
| Camera | No camera code change. The follow keeps tracking the cat as today; the cat is frozen, so the camera settles on it. It snaps on respawn as today. If the existing follow does something else, report it; don't fix it here. |
| Death counter | Report whether a per-room death count (D-044) exists. If not, add a minimal one: a per-room `int` with a read-only accessor, incremented only at a counted kill, never reset by the room reset. No UI. |
| HoldTicks = 0 | Identical to today's synchronous behaviour, same tick. |

Put the counting logic in a pure type in `Parallax.Core` (e.g. `DeathHold`: `Begin(tick)`,
`Step()`, `IsHolding`, `ShouldReset`), unit-tested without scenes, like `TrapTiming`.

## 4a. Tick order

Phase 1 states today's order inside one fixed tick: motor/input, physics result read, trap
phase, kill processing, door check. This ticket keeps that order and inserts:

- the **hold gate** before the trap phase and before door and trigger handling;
- the **bounds check** where other kills are processed, on the position from the last physics
  step.

If a kill and a door touch happen on the same tick, today's behaviour wins. Report which one
that is. With HoldTicks 0 the whole sequence, including that tie, must match today exactly.

## 5. Out-of-bounds semantics

- **Bounds:** for each room, the union of all layout element bounds (both poses for moving
  traps; checkpoint and door included), expanded by the margin on every side. Computed in
  `SoloRoomsSetup` and `TrapLabSetup` from layout data and serialized on the room. State in
  Phase 1 whether they are stored in world or room-local space. The margin lives in the same
  config asset.
- **Room:** the cat is checked only against the bounds of its **current** room (the room
  `RoomManager` considers active), never against the union of all rooms. Neighbouring rooms may
  lie within 2 u of each other.
- **Check:** once per live tick (see §4a), on the cat's centre. Outside → normal kill with cause
  `OutOfBounds`, plus one `Debug.LogWarning` per death with room id and position.
- Not checked during a hold.
- Both gravity directions: a cat falling upward out of the room is caught the same way.
- **Trap Lab:** confirm in Phase 1 that `Sandbox_TrapLab` uses the same room/`RoomManager`
  model. If it doesn't, propose the smallest equivalent or report that bounds don't apply
  there, then stop.

## 8. Tests (EditMode)

1. **Pure hold logic:** counts exactly HoldTicks, reports reset once, ignores a second begin,
   HoldTicks 0 resets on the same tick.
2. **Freeze:** during a hold, `RoomLifeTick`, a `MovingTrap` pose, a falling block and a pending
   chain fire are all unchanged; a chain fire due during the hold does not fire after the reset.
3. **Reset parity:** a room reset after a hold equals a room reset with HoldTicks 0 (every trap,
   the cat, `RoomLifeTick`). Reuse the existing reset tests with both values.
4. **Count:** one death per kill, none during a hold; the count survives the room reset.
5. **Door:** a door touch during a hold does nothing.
6. **Bounds data:** for every room in `SoloRoomsLayout` and `TrapLabLayout`, the computed bounds
   contain every element (both poses) plus the margin.
7. **Out-of-bounds kill:** a cat moved below, above, left and right of the bounds is killed with
   cause `OutOfBounds`; a cat inside is not.
8. **Regression:** every existing test passes. Tests that assume a synchronous reset keep
   HoldTicks 0 or step through the hold; list each one you changed and why. Do not weaken any
   assertion. The test assembly does not reference `Parallax.Editor`: reach editor types by
   reflection, as `SoloRoomsLayoutTests` does. Do not add assembly references.
9. **Input discard:** a jump pressed during the hold produces no jump on tick 0 after the reset.
10. **Spawn inside bounds:** for every room, the checkpoint (cat collider at spawn) and the door
    lie inside the bounds, so a respawn can never be an immediate out-of-bounds death.
11. **Freeze keeps contacts:** a frozen cat inside a trigger during the hold produces no exit
    event (or, if the chosen freeze method does produce one, it has no effect on trap state).
    Adapt to the method approved in Phase 1.

**Baseline:** the developer's total after PAX-046 (confirm it at the start). Report baseline →
new, with every new test listed by name.
