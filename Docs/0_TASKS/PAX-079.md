## 1. Why

The coyote and jump-buffer windows are float countdowns: `timer = max(0, timer − dt)`, with a jump
allowed while `timer > 0`. PAX-077 (R8) found the tick counts depend on float remainders:

| Step | Coyote (airborne ticks a jump is allowed) | Buffer (ticks including the press) |
|---|---|---|
| `0.02f` | 4 | 5 |
| committed 0.0199999929 (abb55f9) | **5** | **6** |

The committed step leaves 4.5e-8 s after five decrements, and that remainder is the only thing
keeping the fifth coyote tick. Any timestep re-save, or a change to the order of the float
operations, can silently change how the game feels. Every level since abb55f9 was played at 5 and
6, so those are the values to lock.

## 2. What to build

1. **Count both windows in whole ticks.** Each window's length in ticks is derived from the
   config's seconds by rounding to the nearest tick:
   `round(CoyoteTime / SecondsPerTick)` = 5, `round(JumpBufferTime / SecondsPerTick)` = 6.
   `CatMotorConfig` keeps its seconds fields, so no asset or prefab changes.
2. **Semantics, stated exactly and tested:**
   - **Coyote:** after the cat leaves the ground, a jump is allowed on the first N airborne steps
     (N = 5).
   - **Buffer:** a press is honoured on the step it happens and the next M − 1 steps (M = 6),
     including the press step.
   - Phase 1 confirms these match what the current code does at the committed step. If they
     don't, the current behaviour wins, and it's restated here in §11.
3. **Unchanged:** Freeze (D-059: `Step` no-ops, the counters don't advance), pause (D-073: the
   counters freeze and continue), and the dt passed to `Step` for everything else (velocity,
   gravity).
4. **Where the rounding lives:** Phase 1 proposes either a `TickTime` method (for example
   `ToWholeTicks(float seconds)` using `Mathf.RoundToInt`) or rounding at the call site. PAX-077
   R6 kept `TickTime` float-only because nothing needed an integer; this is the first caller.

- **R1. Design: keep the float fields and add a pure helper that counts in ints.**
  - `coyoteTimer` and `jumpBufferTimer` keep their names and their float type. Their unit is now
    whole ticks remaining, and 0 means the window is closed. Put a comment on both fields that
    names D-077 and the two reflection tests that depend on them.
  - New pure type `Parallax.Core.JumpWindows` in `Assets/_Game/Core/Physics/JumpWindows.cs`. It
    works in int. The motor converts at the call only, with `(int)` in and `(float)` out, so no
    arithmetic is ever done on the floats.
  - `CatMotor2DFreezeTests.cs` and `PauseInputTests.cs` stay unchanged. §6 is not extended.
- **R2. Semantics: "the ground always allows a jump", with no n + 1.** Per step, in this order:
  1. A press sets buffer = M.
  2. If grounded, set coyote = N.
  3. The jump fires if buffer > 0 && (grounded || coyote > 0).
  4. A jump sets both to 0.
  5. buffer counts down by 1. coyote counts down by 1 only on an airborne step. Neither goes
     below 0.

  This matches the Phase 1 proposal step for step: the state after every step is identical, and
  `coyoteTimer = 1f` on an airborne cat still opens the next step. If a sequence exists where the
  two differ, stop and post it.
- **R3. Old behaviour must match at the real step, proven by an equivalence test.** In the test
  file, build a reference model of today's float logic: `SetCommand`, the countdowns at

  every step:
  - every (grounded, pressed) sequence of length 8 (65,536 of them);
  - 2,000 seeded random sequences of length 60.

  Test: `JumpWindows_MatchesFloatModel_AtCommittedStep`. See it red by mutation: set M = 5 and
  quote the first failing sequence. Stop if it fails for real and post the first failing sequence.
