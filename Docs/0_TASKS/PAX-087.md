## 1. Why

Vines turn walls into routes: climb up, then leap off to a platform. The art already exists (`Assets/_Game/Art/RealityA/Environment/A_OBJ_Vine.png`, 236 × 433). The developer chose stick up/down to climb, so the input gets a vertical axis for the first time.

## 2. What to build

1. **Climb axis.** `CatCommand` gains `float Climb` (−1..1, **screen-up positive**, D-049). Default 0, so every existing path is unchanged.
   - Touch: the stick's y through `VirtualStick` with its own dead zone (default 0.35, higher than x's 0.15 so a slightly diagonal run never reads as climbing).
   - Keyboard: W/S and Up/Down.
   - `CatInputRouter` merges it like `Move`. Echo (frozen) ignores it; confirm in Phase 1.
2. **Element `Vine`** (appended): x centre, bottom y, height, width 0.6 (grab box). Built with the vine sprite tiled vertically (`SpriteDrawMode.Tiled`) if Phase 1 confirms the importer allows it; otherwise a placeholder colour and a note for the art ticket.
3. **Climbing state** (pure `ClimbState` in Core, small `CatClimber` in Gameplay, consulted by the motor):
   - **Grab:** the cat's collider overlaps a vine and `|Climb| ≥ 0.5` (grounded or airborne). No automatic grab: touching a vine without pushing up/down does nothing.
   - **While climbing:** the motor applies no gravity; x snaps to the vine centre on the grab tick; vertical velocity = Climb × `ClimbSpeed` (default **4 u/s** = 0.08 u/tick), screen-relative; the cat can't climb past the vine's top or bottom (it stops there). `Move` alone does nothing.
   - **Leap off:** a jump press while climbing detaches with the normal jump launch (1.6 u apex) and horizontal velocity `sign(Move) × MaxSpeed` (straight up if Move is 0). `Move` is read *after* the inverter (D-087), so an inverted cat leaps the other way; `Climb` is never inverted.
   - **Release:** climbing down past the bottom, a gravity flip, a death, a room reset, a respawn or a launch (`ApplyLaunch`) releases the vine. After a release or leap the cat can't regrab the same vine for `RegrabLockTicks` (default 10).
   - Coyote after a leap: none (like a jump). Buffered jump on the grab tick: leaps.
4. **Snap trap (optional per vine):** a vine can take trap settings (Overlap trigger or Chain, Once, `DelayTicks`). When it fires, it vanishes and releases the cat (a fake-platform-style reveal, D-080 (1)). Resets with the room.
5. **Presentation:** a climb pose in `CatAnimStateMachine` (reuse Walk frames rotated or the Idle frame until the art ticket delivers a climb sheet; no Animator, D-036).
6. **Routes.** `Hold(Up)`, `Hold(Down)`, `ReleaseClimb()` and condition `Climbing()`; the per-tick record gains `IsClimbing`. Existing routes replay byte-identically (Climb = 0).
7. **Validator:** `ValidateVine` (inside the frame, overlaps no solid, height ≥ 1.5, bottom reachable: on a floor or within a jump's reach), `ValidateBand` (levels 11+ only). Leaps off a vine are timed/route-proven, not static `RequiredJump`s, unless Phase 1 finds a cheap way.
8. **Trap Lab room 9:** a tall wall with two vines. The obvious vine snaps halfway up (Dies in the pit below, lead ≥ 6); the real one reaches a ledge you leap onto. Solution + one Dies + one Recovers.

## 11. Rulings (Phase 1, 2026-09-26, HEAD 350da16)

**Status:** Ruled. Go to Phase 2. Baseline 900. Where these differ from §2–§6 they amend the ticket.

**Accepted as traced:** §3 answers 1–5, the motor branch as an early return after the gravity step (with Climb = 0 nothing on the current path changes), the release causes (`ResetMotion` for death/reset/respawn, `ApplyLaunch`, a gravity-side change), the driver zeroing Climb while seated (`SeatCommandFilter` untouched), and the route-format change (`Vertical` enum, `Hold(Vertical)`, `ReleaseClimb()`, `Climbing()`; `Release()` still clears only Move; no route file changes).

### R1 · Keyboard: Space is the only jump key

Approved. Space = jump. W/Up = climb up. S/Down = climb down. A/D and Left/Right keep moving. The keyboard is Editor/dev input (the shipped game is touch), so the cost is small, and the other choice makes climbing up untestable by keyboard. Put the key-to-command mapping in a small pure function with its own tests. D-089 records the key change.

### R2 · Stick: rescaled, option (a)

Approved: `Climb = sign(y)·(|y| − 0.35)/0.65` on `VirtualStick`'s already dead-zoned output (0 inside 0.35). Grabbing then needs roughly 42° above horizontal at full push. That's what we want: a sloppy diagonal run never grabs, and grabbing needs a clear push up. The Phase 2 angle sweep through `VirtualStick` reports the smallest angle that reaches the 0.5 grab threshold at full push. **Stop condition:** if any push within 30° of horizontal grabs, stop and report. Climb speed scales with the rescaled value (a shallow push climbs slower); routes always use full magnitude (D-081 (4)).

### R3 · Vine sprite: stacked Simple segments, no `.meta` change

Approved. Each child renderer uses the vine sprite scaled to width 0.6 (≈ 1.1 u per segment); the top segment is squashed so the vine ends exactly at its authored top. No `.meta`, no `SpriteDrawMode.Tiled`, no new warnings. The art ticket may later switch the importer to Full Rect and use Tiled. All segments sit in the vine element's subtree, so a snap (renderers off) is the vine's visible reveal for the route validator.

### R4 · Files outside §6: all four approved

- `RouteReplay.cs`: runner, `Snapshot`, and the hesitate insert carrying Climb. Keep the change minimal.
- `RouteRecord.cs`: `TickRecord` gains `IsClimbing` and `Climb`, both 0/false on every existing route. While you're in the file, fix the stale comment that says the last extra element is `Cat.Gravity` (it's `Cat.Inverted` since PAX-085).
- `CatMotorConfig.cs`: `ClimbSpeed` 4, `RegrabLockTicks` 10, `GrabThreshold` 0.5, as field initializers. Don't hand-edit the `.asset`. If Unity rewrites it on save, it's a developer step in §9.
- `CatAnimState.cs`: add `Climb` **at the end** (no renumbering). Until the art ticket brings a climb sheet, the presenter shows the Idle frame for `Climb`. Nothing else in the state machine changes except entering and leaving `Climb`.

Guard, as before: every existing route result and every `RouteHarnessFidelityTests` pin stays **identical**. A moved pin is a stop condition.

### R5 · Two rules the trace left open

1. **Grabbing from the ground needs up.** A grounded cat grabs only with Climb ≥ +0.5. Pushing down while standing at a vine's foot does nothing, so the cat never gets stuck at the bottom. An airborne cat grabs with |Climb| ≥ 0.5, in either direction.
2. **Where climbing stops.** At the top: the cat's collider **bottom** stops at the vine's top, so a vine whose top is level with a ledge lets the cat leap straight onto it. At the bottom: climbing down below the vine's bottom releases the cat, which falls (§2.3), or lands if there's a floor. ValidateVine's "bottom reachable" clause uses the grounded grab from rule 1: the bottom is on a floor, or within a jump's reach of one.

### R6 · Your defaults: accepted

- Pure `ClimbState` in Core.
- `CatClimber` is a plain class owned by the motor, not a component; `Cat_Player.prefab` untouched. Keep `CatMotor2D` well under 400 lines.
- The driver finds the reality's `ClimbVine`s when it activates and hands them to the motor, the same way it finds inverters. Include inactive objects. Only the LocalHuman cat can climb.
- The grab test is plain bounds math, not a physics query.
- `ClimbVine` builds on `RoomTrap`. Without snap settings it never fires. A fired snap releases the cat on that tick's room step, and the cat falls from the next motor step.
- `ValidateVine`'s extra clause (the cat, snapped to the vine's centre, overlaps no solid) is approved.
- Leaps off vines are proven by routes as timed steps, not `RequiredJump`s.
