## 1. Why

- **Every shipped check is hand-written.** Every timing check on a shipped level so far was
  written per room:
  - `ShippedLevelTimingTests` (PAX-078);
  - the `SoloRoomsLayout` narrative tests;
  - `RoomStepper`, a narrow model whose assumptions (D-076 (3)) are known to be wrong for some
    rooms.
- **PAX-078 showed what that costs.** A simulator missing the solid landed blocks called L004
  unsolvable. Two 50 Hz gaps in shipped levels were caught only because someone had written
  those exact narratives.
- **D-069 (1) already requires the proof.** Every level must have at least one valid route that
  passes the validator. Nothing enforces that yet.
- **KIT-3b and Phase D depend on it.** They add multi-route sections and 46 more levels, and
  hand-written narratives won't scale to that.

KIT-3a makes a room's anatomy **data that the validator replays through the real game code**:

- **The solution route:** it must reach the door alive, with D-056 (1) slack on every
  timing-critical step.
- **Betrayal routes (the obvious routes):** each must die, at the element the room says kills it,
  with the D-057 lead measured rather than assumed.

## 2. What to build

1. **A replay harness in the Editor assembly.** It builds a level's room from its layout into a
   temporary in-memory scene, the same way `SoloRoomBuilder` builds shipped scenes. Then it steps
   the **real** game code once per tick, driven by a scripted input source:
   - the motor, `RoomManager`, traps, hazards, the door, `RoomDeath`;
   - `Physics2D.Simulate(SecondsPerTick)`.
   It reports per tick: the cat's position, grounded state and gravity; every trap's fire tick and
   visible state; the death tick, cause and killing element; and door completion.
   - The harness reads no saved scene and saves nothing.
   - Tests reach it by reflection, as with other Editor code.
2. **A route format.** A short list of scripted actions with conditions, authored in code-as-data
   next to the layouts (D-066). Phase 1 proposes the exact actions (§3.3). My sketch:
   - `Run(Right, untilX: 14.2)`;
   - `Stop()`, `Wait(ticks)`, `WaitUntil(trap "ArrowA" stopped)`;
   - `Jump()`;
   - actions marked **timed** are swept for slack (§2.4).
3. **Routes for every `LevelLayouts` entry (L001–L004) and for Trap Lab room 3 (arrows).**
   - One solution route per room.
   - One betrayal route per betrayal the room claims, with the expected outcome: the killing
     element and the death cause.
4. **The validator rule** (separately named, e.g. `ValidateRoutes`), per room:
   - **(a) Solution:** the route completes the room. For each timed action, sweep its start tick
     and find the contiguous window of start ticks that still completes the room. The window must
     be at least 12 ticks wide (D-056 (1)). Phase 1 defines "window" exactly (§3.4).
   - **(b) Betrayals:** each betrayal route dies at the expected element and cause. The killing
     element's first visible change comes at least 6 ticks before the death (D-057), measured in
     the replay.
   - **(c) Determinism:** two replays of the same route give the same per-tick record.
5. **Fidelity first (PAX-078's lesson).** Before any route result is trusted, the harness must
   reproduce known numbers:
   - basic motion in a synthetic flat room (run distance per tick, jump apex, coyote and buffer
     counts from D-077);
   - PAX-078's stepped figures: the L002 Lift slack of 14–15 ticks and the L004 `Block_1` visible
     lead of 13–14 ticks, within ±1 tick.
   A mismatch stops the ticket with the numbers.
6. **Housekeeping from KIT-2:** move the six arrow rules out of `LevelLayoutValidator.cs` into
   `LevelLayoutValidator.Arrows.cs`, as a `partial class` of the same type. The type name and the
   method names don't change, so reflection lookups keep working. There's no behaviour change.

## 4. Rules

- No runtime behaviour change. No layout change to L001–L004 or Trap Lab. No threshold change
  (12, 6, 30, 0.12 u).
- The harness runs only in the Editor and in tests. Nothing ships in the player.
- Deterministic: the same route gives the same record every time. No `Time.time`, no randomness.
- No scene or asset is saved by the harness or its tests. The open scene stays clean after a run.
- No new Unity package. No `ProjectSettings/` changes.
- New validator rules go in separately named methods, never in or named `Validate`. Changing an
  existing test needs my approval by name.
