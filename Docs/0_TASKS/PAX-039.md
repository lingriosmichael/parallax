TASK: PAX-039 TITLE: Gravity up/down only: vertical-only gravity, instant flip, screen-relative movement PHASE / GATE: Pivot cleanup (D-037, D-045, D-047). Solo only. PAX-037 is deferred; PAX-038 is retired. Replaces the earlier untracked PAX-039 draft (room model), which moves to PAX-040.

OBJECTIVE Gravity is only ever straight down or straight up. Changing it is an instant flip, never a rotation through sideways. When the cat is upside down, pushing right still moves it right on screen. Nothing sideways can be configured, requested or saved.

CONTEXT

D-037 (gravity up or down only; the debug control becomes a single flip key; the spawn-point validator rejects sideways; D-021 reopened), D-045 (tilt removed), D-047 (solo only; co-op code stays untouched), D-020 (world-aligned camera), D-021 (cat-relative stick; ScreenRelative kept behind projection on TouchStickCatInput).
02_ARCHITECTURE.md §5.1 (movement input), §6 (GravityReceiver, motor, "only SetTargetDirection changes gravity"), §11 (checkpoint markers carry a gravity direction).
Problem today: GravityReceiver turns Direction toward the target at turnSpeedDegPerSec (360°/s). A down→up change therefore passes through sideways gravity for ~0.5 s, pushing the cat sideways mid-flip. At exactly 180° the turn direction is also ambiguous.

DESIGN (record as D-048 and D-049)

Vertical only. Every gravity direction is quantized to (0, −1) or (0, 1). Any request with y < −0.1 becomes down, y > 0.1 becomes up; anything flatter (including zero) keeps the current side.
Instant. Direction equals the quantized target on the next tick; there is no turn speed. The motor already re-projects velocity onto the new down, so momentum carries through the flip. The capsule is symmetric under a 180° rotation, so the instant body rotation does not overlap geometry.
Screen-relative movement (D-049). With walls gone, ScreenRelative has no dead case (its only weakness in D-021 was walls), and it matches the genre convention (VVVVVV): left is always screen-left. Keyboard and touch must behave the same.
Co-op code (Control Station, GravityDial, GravityControlMapping, GravityControlReceiver, Echo) is not changed (D-047). Its requests pass through the same quantization, so it cannot produce sideways gravity.

D-048 · <date> · Accepted
Decision: Gravity is vertical-only in code. Every direction passed to GravityReceiver is quantized to (0, −1) or (0, 1) (|y| ≤ 0.1 keeps the current side) and applied instantly, with no turn speed. GravityReceiver.Flip() is the flip; the debug control is a single key (Q). Validators reject any serialized non-vertical gravity. Why: D-037. Turning at 360°/s passed through sideways gravity for ~0.5 s on every flip, pushing the cat sideways, and the 180° turn direction was ambiguous. Quantizing at the receiver means no caller, including untouched co-op code, can produce sideways gravity. Supersedes: the turn-speed behaviour in 02_ARCHITECTURE §6 (PAX-010). Consequence: the Control Station dial (co-op, untouched per D-047) can only produce down with its current mapping; the co-op update replaces it with a flip.
D-049 · <date> · Accepted
Decision: Movement is ScreenRelative for touch and keyboard: pushing right moves the cat right on screen in both gravities. Why: D-021 chose cat-relative because on a wall ScreenRelative has no useful axis. D-037 removed walls, so that case is gone. Screen-relative matches the genre convention (VVVVVV) and removes the "controls reversed" death that ragebait must not have (D-040). Supersedes: D-021's cat-relative reading. The virtual stick itself (floating origin, jump button) stands. Consequence: confirm on device in PAX-037 when it runs.
