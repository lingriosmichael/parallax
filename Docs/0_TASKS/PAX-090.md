## 1. Why

Levels 11–20 are 30–45 s long and chaotic (`Docs/Design/L011-L020_concepts.md`, all ten approved). With today's rule, a death in act 3 replays everything before it. The developer's call (2026-09-26): keep the long levels, and add **checkpoints in certain sections** so a death only replays the current section. Level Devil gets the same effect with short stages.

## 2. The model (the Architect's design; Phase 1 checks it can be built)

A level stays **one scene, one room, one continuous space, one camera frame**. What's new is that the room can be divided into **sections**.

1. **Sections in the layout.** `SoloRoomDefinition` gains an optional `Section[] Sections`. Each has a `Name`, a **checkpoint** (spawn position and gravity), a **gate** (a trigger box), and the names of the elements it **owns**. With no sections declared, the room is one implicit section and behaves **exactly** as today. Levels 1–10 and every Trap Lab room stay byte-identical in behaviour.
2. **The gate.** Crossing section N+1's gate (the LocalHuman cat's collider overlaps it, on a live, non-holding tick) makes N+1 the current section. Gates are passed in order only: gate N+2 is ignored until gate N+1 is passed. There's no teleport, no fade and no pause; the player keeps running. A checkpoint marker (the existing checkpoint art) lights up at the gate as feedback.
3. **The snapshot.** On the tick a gate is crossed, the room takes a snapshot of every element's state plus `RoomLifeTick`. Traps are pure functions of ticks (D-051, D-055), so an element's state is small: fire tick, armed/rearm state, chain state, repeat counters, and the few extras (a stuck spear, an inverter's window, a cloud's awake flag and x, a snapped vine).
4. **Death rewinds to the gate.** After the death hold (unchanged), instead of resetting to the authored state:
   - `RoomLifeTick` goes back to the snapshot's tick;
   - every element restores its snapshot state (elements that hadn't fired yet are simply unfired);
   - the cat respawns at the current section's checkpoint, at rest.
   - With no gate crossed, the snapshot is the room's start, so this *is* today's reset. D-041's "every trap returns to its initial value" becomes "every element returns to its state when you reached the current checkpoint".
5. **Everything stays live.** Unlike separate rooms, every element keeps ticking and can kill in every section. Walking back into an earlier section works (levels 17 and 20 need it). Section ownership only matters for validation and reporting.
6. **Death count:** kept per section for the stats log; the level-complete screen still shows the level total (D-061 unchanged).
7. **The camera** follows the cat as today and snaps on respawn (D-071, unchanged).

### Rules the validator checks (new, separately named, and added to `ValidateKit` in PAX-089's aggregator)

- `ValidateSections`: gates in order along the solution; each checkpoint inside the frame, standable, and on the far side of its gate; every element owned by exactly one section; sections only in levels 11+ (`ValidateBand`), or allowed everywhere? **Phase 1 Q6.**
- **Respawn safety:** replaying the solution to each gate, then respawning the cat at that checkpoint and standing still, the cat survives at least **50 ticks** (1 s). No respawn straight into a cloud strike, an arrow lane or a closing floor.
- **Replay budget:** the solution time from each checkpoint to the next gate (or the door) is at most **20 s** (1000 ticks). That's the retry cost per section, which is the point of the ticket.

### Routes

- The level still declares one solution route.
- A betrayal route can start at a section: `Route.FromSection(name, …)` replays the solution to that gate, applies a death-and-rewind (or starts from the snapshot, whichever Phase 1 finds cleaner), then runs the betrayal's steps. Leads and killers are measured exactly as now.
- A new route check proves the rewind is exact: replay to gate N, die, rewind; the per-tick record of the next K ticks must equal a fresh replay from the same snapshot (D-079 (3)'s determinism, extended).

## 3. Item B · The vine grab direction (for level 16)

PAX-087 R5 says "a grounded cat grabs only with Climb ≥ +0.5". For a cat standing on the ceiling (gravity up), screen-up points into the ceiling, so it can never grab a vine from the ceiling. The fix: **a grounded cat grabs by pushing away from the ground**, which is screen-up with gravity down (unchanged) and screen-down with gravity up. Airborne grabs are unchanged (|Climb| ≥ 0.5). Climbing itself stays screen-relative (D-049). Test red-first: a gravity-up cat on the ceiling grabs a vine by pushing down, and doesn't grab by pushing up. Every existing pin stays identical (no gravity-up grab exists in any route).

## 5. Phase 1 (Full, ≤ 150 lines; at most 6 questions)

1. **State inventory.** List every runtime field on every `RoomTrap` subclass (and `RoomDoor`, `DoorRetreatTrap`, collapsing/fake platforms, the inverter window, the vine climber's hold on a vine) that changes after the room starts. That list is the snapshot. Propose the interface (e.g. `IRoomSnapshot { object Capture(); void Restore(object); }` or a struct per kind) and say which classes need it.
2. **Rewind vs reset.** Can every element's restore be built from its existing `ResetToInitial` plus its captured fire tick (replaying its pure timing), or does any element hold state that isn't a function of ticks (physics bodies: falling blocks and moving Solids mid-motion, the cat on a moving Solid)? Name each one and how it restores its pose.
3. **Frozen and shared code.** Does any of this touch `CheckpointManager`, `CatRespawn` or `RoomManager` in ways that affect `Sandbox_Realities` / `Level_Solo01` (frozen scaffolding, multi-room)? The implicit single section must leave them byte-identical.
4. **Routes.** Starting a betrayal from a section: replay-to-gate plus a rewind, or start from a captured snapshot? Which is smaller and exact?
5. **Physics on rewind.** Rigidbodies moved by restore need to be at their snapshot pose before the next physics step. Show the tick order that guarantees it in Play and in the harness.
6. **Band.** Should sections be allowed in levels 1–10 (they don't need them) or be levels-11+ only like the kit? Proposed: allowed anywhere, used from 11.

## 6. Rules and stop conditions

- A room with no sections behaves exactly as today: every existing test and pinned route result is **identical**. A moved pin is a stop condition.
- Rewind is exact and deterministic (same input, same outcome from a checkpoint, every time).
- No teleport, no fade, no scene reload; death to control stays ≤ 0.75 s (D-041).
- If any element's state can't be captured and restored exactly, stop and report it by name. Don't approximate.
- Frozen co-op code untouched.

## 11. Rulings (Phase 1, 2026-09-26)

**Status:** Ruled. Go to Phase 2, red-first. Baseline 1074 (or the developer's Run All if different). No stop on Q1: every element's state can be restored exactly.

**Accepted as traced:**
- **Q1:** the state inventory and the interface: `IRoomSnapshot` (Core) with a plain `TrapSnapshot` struct (State, timing state, countdown state, plus one int, one float and one Vector3 for extras; no boxing, comparable by value). `RoomTrap` implements the base; subclasses override `CaptureExtra`/`OnRestore`, with a no-op default. `RoomManager` holds the snapshot. A sectioned room rejects room-owned anchors: a validator error, plus a runtime error log.
- **Q2:**
  - Kinematic bodies restore to `pose(T)` from their formula, then `MovePosition(pose(T))`, never the captured `body.position`.
  - The cloud's `OffsetX`, the retreated door pose and the flip countdown are captured by value.
  - The cat respawns at rest.
- **Q3:** gates don't use `CheckpointMarker` (marker art only). Respawn goes through `CatRespawn.RespawnAt(sectionSpawn, gravity)` from `RoomDeath.PerformReset`. Sections are serialized as `RoomSectionEntry[]` on `RoomManager`, written by `SoloRoomBuilder.BuildRoom` only for rooms that have sections. With no entry, today's code path runs unchanged. `CheckpointManager.cs` and `CatRespawn.cs` stay untouched.
- **Q4:**
  - Replay to the gate, then the real death and rewind: `Route.FromSection(solution, gate, name, …)` plus `R.Rewind()`.
  - One forced rewind per rig, because of `CatRespawn`'s same-frame guard.
  - The rewind-equality check uses two fresh rigs with different pre-death input and compares K recorded ticks.
- **Q5:** on the rewind path only, `RoomLifeTick := T` is set inside `PerformReset`, and `OnDied` doesn't set `roomLifeStartsNextStep`. Today's reset path, including its `HoldTicks = 0` falling-block quirk, stays exactly as it is; D-091 notes the quirk.
- **Q6:** sections are allowed in every level and used from 11 on. `ValidateBand` unchanged.

## 12. Ruling on the contact-cache finding (2026-09-27)

**Approved:** clearing the cat's cached Box2D contacts on the **rewind path only**, so a rewind doesn't depend on where the cat died. It's a physics-engine detail, not game state, and exact rewind (§6) matters more.
- **Mechanism:** toggle `Rigidbody2D.simulated` false → true after the respawn. **Not** `GameObject.SetActive` or disabling components: that would fire `OnDisable`/`OnEnable` on the cat's components and clear state we don't want cleared. Confirm which one you used. If it's anything other than `simulated`, switch to it, test-first.
- **Test:** no component on the cat receives `OnDisable`/`OnEnable` during a rewind, and the L007 two-replay equality stays green.
- Today's reset path stays untouched (levels 1–10 pins). D-091 (3) records the rule as written.
