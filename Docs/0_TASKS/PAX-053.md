## 1. Why

Three problems came out of PAX-051/052, and one feature is due:

- **Build Settings drifted.** The committed list lost `Level_004`, and Unity's in-memory list
  contained `_LevelTemplate`. With 50 levels, a hand-maintained or half-saved list will break
  again.
- **You could play `Level_004` in the Editor even though it wasn't in Build Settings.** On the
  phone the same Next level tap would fail. The Editor must fail in the same way the device
  does.
- **`LevelCompleteUISetup` only runs in `Level_Solo01`.** Under D-070, level UI changes must go
  through `_LevelTemplate`.
- **Feature:** v1 needs a level select screen: pick any unlocked level, and see your best deaths.

## 2. What to build

### 2.1 Generated scene list (D-072)

1. **`BuildSceneList.Sync()`** (Editor) is the only code that writes
   `EditorBuildSettings.scenes`. It produces exactly this list:
   1. `LevelSelect.unity`, enabled (index 0, so the device build starts there);
   2. every `LevelListConfig` entry's scene, enabled, in list order;
   3. then every other scene already in the list, keeping its enabled state and order
      (`Sandbox_Realities` and the disabled dev scenes).

   `_LevelTemplate` and any scene under `Scenes/Levels/` that isn't listed are always removed.
2. **It saves to disk explicitly.** Phase 1 names the call that persists the list; the list must
   survive an Editor restart.
3. **It is idempotent.** Running it twice leaves `ProjectSettings/EditorBuildSettings.asset`
   byte-identical.
4. **Who calls it:** `New Level…` (replacing whatever it does now), the level select setup menu,
   and a menu `PARALLAX/Setup/Levels/Sync Build Scene List`. Remove every other write to
   `EditorBuildSettings.scenes` in level code.

### 2.2 Loading only through Build Settings

1. **All level and menu scene loads go through one runtime loader.** It covers Restart, Next
   level, Level select and loading from the level select screen. It loads by scene name with
   `SceneManager`, and nothing else.
2. **No Editor-only fallback.** If Phase 1 finds an Editor-only load path
   (`EditorSceneManager.LoadSceneInPlayMode`, a load by asset path, a `#if UNITY_EDITOR`
   branch), remove it.
3. **A scene that isn't in Build Settings fails loudly.** Before loading, the loader checks
   `Application.CanStreamedLevelBeLoaded(name)`. On failure it logs an error naming the scene
   and stays on the current screen. In the Editor this gives the same failure you'd get on the
   phone.

### 2.3 Level select

1. **New scene** `Assets/_Game/Scenes/LevelSelect.unity`, built by the menu
   `PARALLAX/Setup/Levels/Level Select`. The menu is idempotent and its guard accepts only
   `LevelSelect`. If the scene is missing, the menu creates it.
2. **A scrollable grid** with one button per `LevelListConfig` entry, in list order, generated
   at runtime from the config. The grid must work unchanged for 50 levels.
3. **Each button shows** the level's display name and its best deaths ("—" if never completed).
   A locked level is dimmed and can't be tapped. The first level is always unlocked. Use the
   existing PAX-050 progress rules; don't define new ones.
4. **Tapping an unlocked level** loads it through the loader (§2.2).
5. **Style:** plain, readable UI that fits landscape at 20:9 and 16:9. No new art, no animation.

### 2.4 Level complete screen: template-targeted

1. Retarget `LevelCompleteUISetup` so its guard accepts only `_LevelTemplate` (D-070).
   `Level_Solo01` keeps its current UI and is never modified again.
2. Add a **Levels** button next to Restart and Next level. It goes to `LevelSelect`.
3. The last listed level still has no Next level button (PAX-050). It does have Levels.
4. After running the menu on the template, the developer runs `Rebuild All Levels`.

## 5. Tests (EditMode)

1. **Scene list shape:** `Sync()` produces `LevelSelect` first, then the listed levels in list
   order, then the other scenes. `_LevelTemplate` is never in the list. Test it with a
   fixture config (including an unlisted `Scenes/Levels` scene) without writing the real
   settings, or restore them afterwards.
2. **Idempotent:** a second `Sync()` changes nothing.
3. **Real project:** the current `EditorBuildSettings` equals what `Sync()` would produce, so
   Build Settings can't drift unnoticed. This test fails today if `LevelSelect` is missing.
4. **Loader:** a scene that can't be loaded gives an error naming it and no scene change. The
   loader contains no Editor-only load path; test this through its code seam, not by reading
   source text.
5. **Level select model** (pure logic in `Parallax.Core` or `Gameplay`): for a given config and
   progress state, it produces entries in list order with the right locked/unlocked state and
   best-deaths text. The first level is always unlocked. Include a 50-entry config.
6. **Complete screen:** each listed level scene has a Levels button wired to the loader. The last
   level has no Next level button but does have Levels.
7. **Guards:** Level Select, Level Complete UI and Sync behave per §2. Test the guard
   functions.
8. **Frustum fix** (only if Phase 1 confirms it): the camera with a zero frame doesn't write a
   zero orthographic size and logs once.

Every test must fail before the code exists, for the reason named. No existing test is modified.

## 7. D-072 (write as built)

The Build Settings scene list is generated by `BuildSceneList.Sync()` from `LevelListConfig`:
`LevelSelect` first, the listed levels in order, then the other scenes untouched. The template
and unlisted level scenes are never included. It is saved explicitly and idempotent, and no
other code writes the list. All runtime scene loads go through one loader that uses Build
Settings only, so a missing scene fails in the Editor exactly as it would on the device.
